How a run flows

From one prompt to a change you can trust

Step through a real bug fix. Use the arrow keys or J K to move.

Punch it new in 0.22

From a meeting to a merge-ready MR, asking only up front

Punch it takes meeting notes, an idea, or a ticket all the way to an MR that is ready to merge. It asks its questions at the start, then runs without stopping unless it hits a real blocker. It never merges. Try it on the worked example below, and make the choices yourself.

Where does the work start?

Example: the orders team's planning meeting on 20 Nov, in the orders-service repo
It asks you

Which tickets to create, which one to punch, and the grant for that one branch. From an idea or a ticket, only the grant.

Then it just does it

Build, check against the ticket, push this branch, open the MR, fix CI and review threads, and re-check every fix.

It never

Merges, turns on auto-merge, force-pushes, pushes another branch or repo, or closes anything.

Set up meeting notes once

Keep the notes in their own private repo, one markdown file per meeting named by its date, such as 2026-11-20-planning.md. Clone it next to your other repos, then tell tblock where it is. Each run pulls it first.

tblock notes ~/Developer/team-notes
Claude Code: add the folder to additionalDirectories in ~/.claude/settings.json. Copilot in VS Code: add it to your workspace. tblock doctor checks it.

Agents and roles

Helpers on a short leash

The main agent owns the task, the playbook and the reply to you. It hands bounded jobs to helpers, each with its own memory and the model its role needs, then reviews their work itself.

delegate

One bounded job
  • Gets a code change or a fix, with the files, what done means, and the check to run.
  • Stays inside those files. Never pushes or posts.
  • Returns a fixed report: changed, checked, not checked, decisions.

threepio

Ticket writer
  • Drafts GitLab or GitHub tickets from meeting notes, an idea, or finished work.
  • Every acceptance criterion cites where it came from: a note line, the diff, or a check.
  • Drafts only. A person says yes before anything is created.

checker

Ticket versus branch
  • Checks a branch against its ticket's AC-1, AC-2 lines, read-only.
  • Runs the tests and commands itself, on the current head.
  • Marks each criterion met or missing, and flags changes the ticket didn't ask for.

Review panels

interrogate · ui-council
  • Reviewers on different model families try to break the change.
  • A finding counts only with proof: a run, a screenshot, or a repro.
  • They report. The main agent re-checks and decides.

Why agents and not just skills

Separate memory

Screenshots and long logs stay in the helper's context. The main thread keeps only the summary.

A different model

A skill runs on whatever model is already running. An agent can run on the model its role needs.

A tighter leash

A helper gets a short brief with hard limits, so it can't spawn its own helpers or push.

The know-how stays in skills

Each agent file is about ten lines that point at a skill, so Copilot and Claude Code share one copy.

What it does without asking, and what it never does alone

Just does it
  • Read and edit code
  • Run builds, tests, the app
  • Local commits on a branch
  • Spawn the helpers a step needs
Always asks first
  • Push or force-push
  • Open, approve or merge a PR
  • Post to chat or tickets
  • Deploy, or delete anything

Build a prompt

State the goal and how to tell it's done. Don't list skills: the playbook already knows them.
Does it use more tokens?

Yes, mostly on helpers and review panels. The lean preset keeps that down, and for a one-line edit you can skip tblock-mode. A cheap answer that's wrong costs more once you count the fix.

Can it push or deploy by itself?

No. Pushing, PRs, tickets, deploys and deletes always wait for a clear yes, and a yes covers that one action only.

What if my project has no tests?

Its proof is only as good as the checks it can run. It says what it could not check instead of claiming a pass, and it can set up a verification skill for the project.

How do I find the right skill?

Ask /tblock-help. It maps what you want to do onto the skill or playbook that does it, and fixes runs that went wrong.
